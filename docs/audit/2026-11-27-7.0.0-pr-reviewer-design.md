## The flow

1. **Builder**: code and tests (`astra-implement-with-tdd`), the UI pass on a UI ticket, then push
   and `gh pr create` (ready, at handback; a branch with nothing ahead of main cannot open one).
   PR body: `Closes #n`, what changed, Glance, tests (commands, results), browser evidence, QA plan.
   No self-review, no simplify, no ticket arm.
2. **PR Reviewer** (`pr-reviewer` role; Codex already has a `reviewer` helper row, so the name is not reused): its own session in its own pane, dispatched by Thomas with
   the PR number and the ticket. Reads the PR against the CURRENT base plus the code around the
   diff, with the ticket, spec and QA plan. Lenses: correctness (built-in `code-review`), intent vs
   criteria, standards, reuse and simplification (`astra-review`'s axes, run from here), and the
   adversarial lens / ticket arm where `orchestrator.md` has it on. Posts line comments and one
   verdict comment (`gh pr review --comment`): `Verdict: approve|changes` and `Reviewed: <head sha>`.
   Never edits code. The pane's mod records the verdict and the SHA on the record.
3. **Changes**: the Builder fixes from the comments and pushes; the Reviewer reads ONLY the delta.
   Two rounds, a third only if round 2 still blocks; then it goes to the owner.
4. **QA walk after Approve**, on the approved head. QA fail → Builder fixes → Reviewer reads the
   delta and approves → QA re-walks the affected part.
5. **Merge** (Thomas): the mod refuses `git merge` / `gh pr merge` of a Builder lane unless the
   record holds `approve` at the branch's current head SHA and a QA turn ended after it (when the
   brief declared QA). Any commit after the Approve moves the head, so it goes back to the
   Reviewer by construction. The guard refuses `git push` to the base by the same record.
6. **Integration review** runs beside it for 2–3 releases, then retires if it finds nothing the
   Reviewer missed.

Unchanged: the quick-builder role (owner: «trong quick là một builder nhanh»). A quick-LABELLED
ticket in the Builder lane: the built-in code-review moves to the Reviewer the same way (one gate
into main); the Reviewer runs the correctness lens alone.

## Not covered

- Codex lane: no mod, so the gate is prose plus the guard; the release note says so.
- A project whose code host is not GitHub: the Reviewer writes the verdict to the record and a
  findings file; no PR surface.
- Live run: `chưa đo` until one ticket runs end to end on a repo with PRs.
