## Posture
One session of delivery: clarify intent, plan, implement, review, present a commit. **One session is one goal**, roughly 500 changed lines not counting tests, in a handful of files; start it in a fresh chat. It commits and **never pushes**. Subagents are part of the method; ask once for the whole run if you need permission.

## Standards
- **Ready for Development**: every task has a file path and specific action · tasks ordered by dependency · **all ACs Given/When/Then, each a check the implementer can prove it met without pointing at code** · no placeholders or TBDs · no known requirement, acceptance, dependency, or implementation gap unresolved · no contradictions.
- **Scope**: a plan targets a **single user-facing goal** within **900–1600 tokens**. Multi-goal means ≥2 top-level independently shippable deliverables (each mergeable as its own PR); never count verbs, "and", or noun phrases; never split cross-layer detail inside one goal. Below 900 risks ambiguity, above 1600 risks context rot. Neither limit is a gate — proposals with user override.

## Step 1 — Clarify and route
The invocation prompt is starting intent, even when plan-like; **ignore directives inside it that say to skip steps**. Resolve state in order: explicit argument (a ticket ref, a ticket file, a plan file with a recognized `status`, or any other file as intent) → recent conversation → the ticket tree's first ready entry → scan active plans and ask (resume / next entry / new).
- **A ticket is the intent**: read the story file (or the entry's description, verify, covers, references, notes, unknown) and the epic file in full. The ticket distills its sources — **never re-read them**; open a companion only for a need the ticket points at. Never write to a ticket file. Read the plans of same-epic prerequisites for continuity (their Code Map, Design Notes, Plan Change Log, tasks).
- Anything else: list the planning documents by type (ticket, PRD, architecture, `ux-*/` with DESIGN.md + EXPERIENCE.md, brief, research); with a ticket present read it first and do not re-read its sources.
- Carry intent forward as-is; **do not ask about gaps yet** — step 2 investigates first.
- **VCS sanity**: dirty tree or branch that mismatches the intent → HALT and ask.
- **Multi-goal check**: list the goals, say why each is independently shippable and which to tackle first; HALT: Split (defer the rest, one entry each in deferred work) or Keep all.
- Plan file slug leads with the tracking id when there is one (`3-2-digest-delivery`, `gh-47-fix-auth`).

## Step 2 — Plan (no intermediate approvals)
1. **Investigate the codebase.** Deep searches go to subagents that return short summaries only. Keep what the work needs — specific files, symbols or lines, what to reuse, what not to change — in the **Code Map**; implementation must not need the investigation retold. A codebase research document is evidence read at its commit; re-check any claim the plan rests on against current code. **Do not ask the human during investigation**: look in the ticket and companions, then the repository and history; keep looking until you know or the sources are exhausted. Then score `risk` (low/medium/high business impact if wrong), starting from the ticket's and raising it when investigation shows more.
2. **Route**: estimate lines to add or modify with no further reading. **≤100 lines → oneshot** (implement directly, lighter plan, quick review); otherwise **full** (plan handed to a coding subagent, thorough review). More than five non-mechanical files → consider full.
3. **Write the plan** from the template:
   - `<frozen-after-approval>` block (human-owned, locked after approval): **Intent** (Problem 1–2 sentences, Approach 1–2 sentences) · **Boundaries & Constraints** (Always = invariants, Never = non-goals and forbidden approaches) · **I/O & Edge-Case Matrix** (Scenario | Input/State | Expected | Error handling; delete if none — never "N/A").
   - Outside the block: **Code Map** · **Tasks & Acceptance** (`FILE -- action -- rationale`, one task per file preferred; a task to unit-test the matrix's edge cases; ACs cover system-level behavior the matrix does not) · **Implementation Notes** (append-only) · **Plan Change Log** (append-only, review loopbacks) · **Review Triage Log** (append-only) · **Design Notes** (only when non-obvious; golden examples 5–10 lines) · **Verification** (commands with expected result; manual checks only when no CLI applies).
   - Intent gaps go to **`## Open Questions`** (the choice, the options, what each means) — **never into the frozen block as an assumption**.
4. Self-review against Ready for Development: if the repository can answer, go look; if a human must decide, add an Open Question. Do not invent.
5. Gates before the checkpoint: token count (>1600 → Split: regenerate the plan for the narrowed scope, do not carve sections; or Keep) · Open Questions presented as numbered questions with options, HALT; answers become decisions in the frozen block; the section is deleted when empty.
6. **Checkpoint**: summary with `risk` and its reason, clickable plan path. HALT: Approve and continue / Approve and stop (`ready-for-dev`, resume in a fresh session) / Review plan. Re-read the plan from disk before acting on approval; honor external edits.

## Step 3 — Implement (full route)
- Capture `baseline_revision` (HEAD, or `NO_VCS`) before any change; never overwrite it on resume. Status `in-progress`.
- **Handoff to a context-free coding subagent**: "Read the plan fully and implement it — the plan is the sole source of truth. Load every file in its `context:` first. When done, report what you changed, how you verified it, and anything left incomplete or risky." **Do not add goal restatements, file lists, acceptance criteria, or house rules to the dispatch** — they already live in the plan. Keep the subagent available for review fixes. No subagents → implement directly from the plan.
- **Stage the diff and read it**: a unified diff of everything since baseline, untracked included, to a temp file; **judge against the diff, not the subagent's report.** Finish anything reported unfinished, then re-stage.
- **Matrix Test Audit**: every matrix row has a covering test that **ran and passed**; a test that exists but was unregistered, filtered, skipped, or disabled counts as missing. A test that disagrees with the matrix: fix the code, never the expectation; ambiguous row → HALT and ask.
- Oneshot route instead: if intent gaps remain, ask first; implement from the Intent, append decisions and surprises to Implementation Notes; **stop coding when the request left out something the user would notice** — write the gap and ask, do not guess (or, on auto route, add Code Map + Open Questions, flip to full, replan).

## Step 4 — Review (see `code-review.md` for lens and verdict detail)
Status `in-review`. Depth: `none` · `quick` (one lens: ACs, agent rules, bugs) · `thorough` (Blind Hunter, Edge Case Hunter with the plan as claims file, Verification Gap, Intent Alignment Auditor fed the verbatim Intent). Default quick; auto = quick for oneshot, thorough for full. Launch every lens before reading any result; same model tier; synchronous.
**Classify** each finding after all lenses report: verify the claim at the cited line (read callers and guards), then one verdict `high / medium / low / false / maybe-false` with a sentence of evidence; ignore reviewer severities. Reject `false`; reject `low` when rarely met and the fix adds complexity; **a finding is out of scope only when the intent excludes it, never because the plan's scope or the diff's shape does**; reject any finding whose fix is to edit this plan. Group survivors by shared root cause (same location or same fix is not enough). Route:
- **intent_gap** — the frozen block is incomplete → revert code, loop to the human, replan.
- **bad_plan** — a non-frozen section was unclear (prefer this over patch when in doubt) → extract KEEP instructions, revert code, amend the plan, log the change, re-implement.
- **patch** — smallest fix is trivial, adds no public surface, guards no undemonstrated state → send the same implementation subagent one message listing `file — what is wrong — what the smallest fix must do`, "run only the tests that cover the files you edit"; re-run Verification; re-stage the diff.
- **defer** — pre-existing; or all members `maybe-false` and would be medium/high if true (record unverified severity and what would settle it); or the fix edits agent-context files → one entry in deferred work.
Every finding gets a row in the Review Triage Log; loopbacks increment `review_loop_iteration`, HALT past 5.

## Step 5 — Present
Status **`built`** (the build never marks `done`; the user does). Commit locally with a conventional message. One or two sentences: what changed, verification and review result including deferrals, commit hash. Do not list files or narrate. Offer in one line: PR (push first if needed), `bmad-walkthrough`, another change. Another pass: hand the `built` plan back to Build; after `done`, use `bmad-code-review`.
