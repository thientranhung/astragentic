## Posture
Several independent reviewers hunt for defects in a code change; you send them the change, then **verify, triage, present, and fix** what they found. Reviewers lack context to grade — you do. Modes: interactive (default) or non-interactive (never ask, take the named default; the report text is the deliverable); fixes `apply` (default) or `handoff` (no-code review: inspect only, write a block a coding agent can fix from). Depth `thorough` by default; `quick` on request.

## Step 1 — Gather context (read-only except the staged files)
Find the target in order, stop at the first hit: the request or recent conversation (PR via `gh pr view`, commit, branch, range, staged/uncommitted, pasted diff or file list, **a plan file** — its `ticket` names the ticket to read, its `baseline_revision` makes the diff source the plan baseline) → **the ticket tree** (offer tickets in `review`; a picked ticket's story file or epic file is read in full and its plan taken) → current git state (HEAD off the default branch → confirm a branch diff) → ask.
- **Stage the diff** to a uniquely named temp file outside the repo. Branch diffs run from the merge-base (`<base>...HEAD`). File lists include untracked files. Empty → HALT. **Lenses read the file; diff text is never pasted into a prompt.**
- **Stage the claims file**: the change's own narrative (commit messages over the range, or the supplied description), verbatim, in its own temp file. Not analyzed. **Input for one lens only**, staged separately so the others never see it.
- **Plan context**: "no plan" said explicitly → `no-plan`, do not ask; plan set → `full`; otherwise ask for a plan path or continue without (never assume no-plan). Load the plan's `context:` docs; open a ticket's sources or companions only for a section the ticket cites, never to re-derive requirements.
- Diff > ~3000 lines → warn, offer to chunk by file group.
- **Checkpoint**: diff stats, mode, loaded ticket/plan/docs. HALT for confirmation (interactive).

## Step 2 — Review (parallel, context-free, same model tier, synchronous)
Announce skipped lenses first, then **launch every active lens before handling any result**. Substitute paths (diff, claims, plan, ticket) and the **verbatim intent** (the ticket's Description, Requirements and criteria with its epic's covered Requirements lines; else the plan's Intent; else the user's own words on what the change is for — a request to review is not an intent). Every reviewer prompt ends: review by inspection only, do not modify code or run tests, do not invoke skills or spawn subagents, return findings as text.
**Quick** — one lens: read the ticket, the plan and its context files, the agent instruction files (`AGENTS.md`/`CLAUDE.md` at root and in touched directories — those are the rules), then the diff; report unmet acceptance criteria, broken rules, and bugs with location, what goes wrong, evidence; Markdown list, no severity.
**Thorough** — four lenses:
- **Blind Hunter** — no intent, no plan. "Look for what's missing, not only what's wrong." Finding floor from the diff size: **N = min(floor(sqrt(kB) + 1), 10)**; state the arithmetic, find at least N; zero findings → re-check and keep thinking.
- **Edge Case Hunter** — pure path tracer on the diff hunks; claims file read **only after** tracing (see `review-edge-case-hunter.md`).
- **Verification Gap** — "if this behavior broke, would any test fail?" Four gap shapes: regression gap, missing-adoption gap, broken-verification gap (skipped, flaky, not run, too weak), **stale-verification gap** (a test the change made wrong or moot; it may still pass). Evidence rules: read a test before saying what it covers; search the repo for the symbol before saying no test exists; drop any finding you cannot ground; no severity. Screen out non-behavioral parts and parts not worth a test (static text, prompts, LLM output, build/toolchain/config that CI exercises by building) — but never skip test-only parts. For each consumer name the smallest realistic regression (the **Demonstration**); "this line could be removed without a test failing" is not one; unreachable, defensive, or redundant code → no finding, nowhere else to file it. A test counts only when it runs normally and an assertion observes the changed output; source-text assertions, no-throw/snapshot-only checks, mock- or log-call checks, mocked-away integrations do not count. Output per gap: changed surface, impacted consumer (`file:line`, never "callers of"), existing test evidence, missing verification, demonstration, consequence, disposition (the test to add or change, fit to how this repo tests). Bugs met while tracing go under `Other findings`. Clean: exactly `No verification gaps found.`
- **Intent Alignment Auditor** (only when an intent is available) — fed the verbatim intent and the diff, no other context. Strictly descriptive: (1) the defensible readings of the intent, enumerated; (2) which reading the diff implements; (3) where they diverge — which surface the intent's expectations live at vs which surface the diff and its tests exercise.
No subagents available → write each lens's standalone prompt (files inlined) beside the plan, HALT, ask a human to run them (ideally a different LLM) and paste findings. A lens that fails or returns empty → record in `failed_layers`, continue.

## Step 3 — Triage (the common failures: forgetting a finding; rejecting a real defect because it resembles a rejected one; wrong severity)
1. Wait for **all** lenses. Normalize to `R1, R2…` with source lens, title, detail, location. **Do not deduplicate yet** — it breaks traceability. Write the list to a triage file; a decision not in it does not exist.
2. **Verify the claim**: can the alleged behavior occur at the cited line? Can the program reach that state? Is it actually unwanted? Read beyond the hunk — callers, upstream guards. "Throws when X" is real only if you show X happens; an assert on an unreachable state is defensive programming. **Never judge B by its similarity to A** unless both cite the exact same behavior at the exact same line. Severity, rarity, fixability play no part here. Gap findings from the verification-gap lens arrive **pre-verified** (skip verification); its `Other findings` are verified like the rest.
3. **Severity of real findings** by the harm of a single occurrence to a user or developer, independent of rarity, fix cost, or whether it predates the change. `high` data loss/corruption, security exposure, silently wrong result, path broken with no workaround · `medium` broken but noticed and worked around, or limited reach · `low` cosmetic or minor inconvenience · `false` not real · `maybe-false` cannot decide from diff and surrounding code. Gap findings are `medium` by rule. Developer-only "this is messy" needs a named place it will hurt, else `low` or not a finding. Can't choose medium vs low → medium. **Each verdict carries one sentence of evidence**: the harm; what disproves; what would settle.
4. **Reject**: every `false`; a `low` rarely visible whose fix adds complexity (more than a direct correction or deletion); any finding whose fix is to edit the plan's intent. Rejected findings stay in the file, marked, with the reason.
5. **Group by root cause** into `F1, F2…` — same cause, not similar; same line can hold two bugs. A group carries the highest verdict, the joined sources (`blind-hunter+edge-case-hunter`), and its member ids. Order by verdict.

## Step 4 — Route each `F`
- **decision_needed** — the right fix depends on what the user meant; list the options one line each and recommend one with the reason. **Assign it even in non-interactive mode; never guess and patch.**
- **patch** — unambiguous fix, adds no public surface, guards no undemonstrated state; otherwise decision_needed.
- **defer** — pre-existing and not caused by this change; or all members `maybe-false` and would be medium/high if true (record the unverified severity and what would settle it; if only low, reject with the note); or the fix edits agent-context files (CLAUDE.md, AGENTS.md, rules) or a ticket file. **An entry this change caused, with a verified high/medium/low member, is never `defer`.**
Report failed lenses before results; zero findings plus a failed lens → "may be incomplete", not clean. Zero after triage → "✅ Clean review — all lenses passed."

## Step 5 — Present and act
- With a plan: append a dated block to its `## Code Review` section — summary line, then `[ ] [Review][Decision] … Options … Recommended`, `[ ] [Review][Patch] title [file:line]`, `[x] [Review][Defer] … — deferred: reason`, then a `Rejected` appendix (false with refutation, low with why not worth fixing). Each defer also goes to the deferred-work list. **Never change the plan's `status`** — the build leaves it `built`; only the user marks a ticket done.
- Summary: `<D> decision-needed, <P> patch, <W> defer, <R> rejected.` Without a plan: "Findings are listed above. No plan was provided, so nothing was persisted."
- Resolve decision-needed first (each becomes patch, defer, or rejected; a defer gets a one-line reason). Then patches: apply every patch / leave as action items (plan only) / walk through each. Non-interactive: apply every patch without asking. Handoff mode: one Markdown block naming base and reviewed commit by full SHA, per patch what is wrong and how you know, files or symbols, the fixed outcome (not a recipe), how to check; unresolved decisions and defers listed under their own headings; **never claim a fix works — nothing was run.**
- Next: build the next ticket / re-run review / done. Stop when findings are mostly minor notes on unlikely corners; real findings on a third pass point outside the change (weak spec, unclear repo rules).
